# ADNEXA — นโยบายสำรองและกู้คืนข้อมูล (แผนก่อนเปิดใช้งาน)

> สถานะ: **ข้อกำหนด/แผนงานเท่านั้น ยังไม่ได้เปิดระบบ backup อัตโนมัติหรือทดสอบ restore ใน production** ห้ามสื่อสารกับลูกค้าว่ามีการสำรองแล้วจนกว่าจะตั้งค่าและมีหลักฐานการทดสอบจริง

## 1. ขอบเขตข้อมูลที่ต้องปกป้อง

- บัญชีผู้ใช้และข้อมูลโปรไฟล์ที่จำเป็น
- การตั้งค่าองค์กร/สมาชิก/สิทธิ์การเข้าถึง
- แคมเปญ โครงร่างโฆษณา และประวัติการแก้ไข
- การเชื่อมต่อแพลตฟอร์มและ metadata (ไม่เก็บรหัสผ่านแพลตฟอร์ม)
- รายการชำระเงิน ใบเสร็จ และบันทึกธุรกรรม
- บันทึกความยินยอม เวอร์ชันประกาศ และคำขอใช้สิทธิ
- Audit/security logs ที่จำเป็น

**ไม่ควรสำรอง token หรือ secret แบบ plaintext** หากจำเป็นต้องเก็บ OAuth refresh token ต้องเข้ารหัสด้วย KMS/secret manager จำกัดผู้เข้าถึง และแยกกุญแจออกจากข้อมูลสำรอง

## 2. เป้าหมายการกู้คืน (เป้าหมาย ไม่ใช่สถานะที่รับประกัน)

- RPO เป้าหมาย: ข้อมูลสูญหายย้อนหลังไม่เกิน 24 ชั่วโมง
- RTO เป้าหมาย: บริการหลักกลับมาใช้งานภายใน 8 ชั่วโมง
- สำรองข้อมูลรายวัน และเก็บรายวัน 30 วัน / รายเดือน 12 เดือน โดยปรับตามความจำเป็น ต้นทุน และข้อกำหนดกฎหมาย
- ทดสอบกู้คืนอย่างน้อยทุกไตรมาส และหลังเปลี่ยนระบบสำคัญ

ต้องตรวจสอบความสามารถจริงของ Firebase/Google Cloud, ค่าใช้จ่าย, ข้อจำกัด region และแผนบริการก่อนกำหนด SLA หรือเปิดใช้

## 3. วิธีการสำรองที่ต้องดำเนินการ

1. เปิดใช้การสำรอง/ส่งออก Firestore ตามวิธีที่บริการรองรับ (เช่น scheduled export หรือ backup/PITR ตามความเหมาะสม)
2. เก็บไฟล์ใน Cloud Storage bucket แยกจากฐานข้อมูลหลัก และกำหนด retention/lifecycle
3. เข้ารหัสขณะส่งและขณะจัดเก็บ จำกัดสิทธิ์ด้วย least privilege และเปิด audit logs
4. แยกบัญชี/โปรเจกต์สำรองหรือมาตรการป้องกันการลบโดยผู้โจมตี ตามความเหมาะสม
5. สำรองไฟล์กำหนดค่าและเอกสารระบบ โดยห้ามใส่ API secrets, private keys หรือ service-account key ลง Git
6. บันทึกผล backup ทุกครั้ง: เวลา, dataset, จำนวนเอกสาร/ขนาด, สถานะ, error และ checksum เมื่อทำได้
7. แจ้งเตือนเมื่อ backup ล้มเหลวหรือไม่มี backup ใหม่เกิน 24 ชั่วโมง

## 4. ขั้นตอนกู้คืน

1. ผู้มีอำนาจเปิด incident และหยุดงานเขียนข้อมูลที่อาจทำให้เสียหายเพิ่ม
2. ระบุ snapshot/export ที่ปลอดภัยและตรวจสอบช่วงเวลาที่ข้อมูลถูกต้อง
3. กู้คืนไปยัง project/bucket แยกก่อน ห้ามเขียนทับ production ทันที
4. ตรวจสอบจำนวนข้อมูล ความสัมพันธ์ สิทธิ์ผู้ใช้ consent records และรายการธุรกรรม
5. ให้ผู้รับผิดชอบอนุมัติ แล้วจึงสลับระบบกลับอย่างควบคุม
6. แจ้งผู้ใช้/หน่วยงานตามหน้าที่และกรอบเวลาที่กฎหมายกำหนด หากเป็นเหตุละเมิดข้อมูลส่วนบุคคล
7. บันทึกสาเหตุ ผลกระทบ วิธีแก้ และบทเรียนหลังเหตุการณ์

## 5. Checklist ก่อนเปิดให้ลูกค้าใช้

- [ ] เลือกฐานข้อมูลและ region
- [ ] ประเมินค่าใช้จ่าย backup/export/storage/operations ก่อนเปิดใช้
- [ ] ตั้ง scheduled backup และ lifecycle retention
- [ ] ตั้ง IAM least privilege และ MFA สำหรับผู้ดูแล
- [ ] ตั้ง alert เมื่อ backup fail หรือ stale
- [ ] ทดสอบ restore ใน environment แยก และจับเวลา RPO/RTO จริง
- [ ] ทดสอบกรณีบัญชีผู้ดูแลถูกยึด/ข้อมูลถูกลบ/ข้อมูลผิดพลาด
- [ ] จัดทำ runbook และรายชื่อผู้รับผิดชอบ incident
- [ ] ตรวจสอบ backup ไม่เก็บข้อมูลเกินจำเป็นและลบตามกำหนด
- [ ] อัปเดตสถานะจริงในหน้า admin และเอกสารลูกค้า

## 6. ข้อควรระวัง

Backup ไม่ใช่การป้องกันข้อมูลรั่วไหล และไม่ใช่การเก็บข้อมูลได้ตลอดไป ต้องมีทั้ง access control, encryption, audit, retention/deletion, incident response และการทดสอบ restore การสำรองข้อมูลส่วนบุคคลต้องอยู่ภายใต้วัตถุประสงค์/ฐานกฎหมายและมาตรการคุ้มครองที่เหมาะสมด้วย
